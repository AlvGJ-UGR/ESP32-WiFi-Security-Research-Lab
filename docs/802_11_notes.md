# IEEE 802.11 Protocol — Study Notes

Personal notes compiled while building the analyzer suite. These document what I learned about the 802.11 standard through hands-on work with real captures from the ESP32.

---

## Frame Structure

Every 802.11 frame starts with a **MAC header** followed by a variable-length body and a 4-byte FCS (Frame Check Sequence):

```
┌──────────────┬──────────────┬───────────────────┬─────────────────┬─────┐
│ Frame Control│   Duration   │  Address 1 (Dst)  │ Address 2 (Src) │ ... │
│   (2 bytes)  │   (2 bytes)  │    (6 bytes)      │   (6 bytes)     │     │
└──────────────┴──────────────┴───────────────────┴─────────────────┴─────┘
```

The full 802.11 header for data/management frames is 24 bytes (with a 4th address field in WDS it grows to 30).

### Frame Control Field (2 bytes)

The most important field. Bit layout (little-endian on wire):

```
Bits: 15-12    11-8      7-4       3-2      1    0
      Subtype  Subtype   Reserved  Type     MF   PV
```

Simplified:
- **Bits 0–1**: Protocol Version (always 0)
- **Bits 2–3**: Type — `00` Management, `01` Control, `10` Data
- **Bits 4–7**: Subtype — differentiates frames within each type

In Python: `ftype = (fc >> 2) & 0x3` and `subtype = (fc >> 4) & 0xF`

## Frame Types

### Management Frames (Type = 00)

Used to establish and maintain connections. These are always sent unencrypted — which is why they're visible in monitor mode even on encrypted networks.

| Subtype | Name | Purpose |
|---|---|---|
| 0000 | Association Request | Client → AP: "I want to join" |
| 0001 | Association Response | AP → Client: "Accepted / Denied" |
| 0100 | Probe Request | Client broadcasting: "Who's out there?" |
| 0101 | Probe Response | AP responding to probe |
| 1000 | Beacon | AP broadcasting its presence (typically 10/s) |
| 1010 | Disassociation | Graceful disconnect |
| 1011 | Authentication | First step in joining a network |
| 1100 | Deauthentication | Forced disconnect (notoriously abusable) |

**Key observation from captures**: Beacon frames dominate management traffic. A single AP at 100ms beacon interval generates ~600 beacons per minute. In a dense urban environment this makes management frames the majority of total traffic.

### Control Frames (Type = 01)

Assist in delivery of data frames. Short, no body.

| Subtype | Name | Purpose |
|---|---|---|
| 1011 | RTS | Request to Send — reserve the channel |
| 1100 | CTS | Clear to Send — channel is yours |
| 1101 | ACK | Acknowledgement — frame received |
| 1000 | Block Ack Request | Request batch acknowledgement |
| 1001 | Block Ack | Batch acknowledgement (802.11n+) |

**Key observation**: ACK frames are extremely frequent in busy networks. Every unicast data frame requires an ACK within SIFS (16 µs on 5 GHz). This means roughly 1 ACK per data frame, which shows up clearly in the frame type breakdown charts.

### Data Frames (Type = 10)

Carry actual payload (TCP/IP traffic etc).

| Subtype | Name |
|---|---|
| 0000 | Data |
| 1000 | QoS Data (802.11e) |
| 0001 | Data + CF-Ack |

**Key observation**: In modern WPA2 networks, data frame payloads are encrypted (CCMP/AES). Monitor mode can see the frame header (addresses, sequence numbers) but not the payload.

## Beacon Frame Body

After the 24-byte MAC header, beacons have a fixed parameter section followed by tagged parameters (Information Elements):

```
┌──────────────────┬──────────────────┬──────────────────┬──────────────── ...
│ Timestamp        │ Beacon Interval  │ Capability Info  │ Tagged Parameters
│ (8 bytes)        │ (2 bytes)        │ (2 bytes)        │ (variable)
└──────────────────┴──────────────────┴──────────────────┴──────────────── ...
```

**Beacon Interval**: Time between beacons in TU (Time Units, 1 TU = 1.024 ms). Default is usually 100 TU ≈ 102.4 ms ≈ ~10 beacons/second.

**Capability Info**: 16-bit field. The two most relevant bits:
- Bit 0 (ESS): Set for Infrastructure mode (AP)
- Bit 1 (IBSS): Set for Ad-Hoc mode
- Bit 4 (Privacy): Set if encryption is in use (WEP-era flag, still present in WPA2)

### Tagged Parameters (Information Elements)

Each IE has the format: `[Tag Number: 1B] [Tag Length: 1B] [Tag Data: N bytes]`

Key tags encountered in captures:

| Tag | Name | Content |
|---|---|---|
| 0 | SSID | Network name (UTF-8). Empty = hidden network |
| 1 | Supported Rates | List of rates × 0.5 Mbps, top bit set = basic rate |
| 3 | DS Parameter Set | Current channel number (1 byte) |
| 48 | RSN (WPA2) | Cipher suites, AKM suites — presence means WPA2 |
| 50 | Extended Supported Rates | Additional rates beyond tag 1 |
| 221 | Vendor Specific | OUI-prefixed. OUI `00:50:F2:01` = WPA1 (Microsoft) |

**Encryption detection logic used in the parser:**
1. If RSN IE (tag 48) present → WPA2
2. Else if Vendor IE with OUI `00:50:F2:01` → WPA
3. Else if Privacy bit set in Capability Info → WEP
4. Else → Open

## Radiotap Header

Not part of 802.11 itself — added by the capture driver (Linux mac80211, ESP32 promiscuous callback) to carry PHY-layer metadata that isn't in the 802.11 header.

Structure:
```
┌──────┬─────┬────────────┬──────────────────┬───────────────────────────┐
│ Ver  │ Pad │ Header Len │ Present Flags(4B) │ Fields (variable, aligned) │
│ (1B) │(1B) │   (2B)     │ (can repeat)      │                           │
└──────┴─────┴────────────┴──────────────────┴───────────────────────────┘
```

**Present Flags**: Each bit corresponds to a field. If bit N is set, that field is present in the header body. Fields appear in bit-number order with natural alignment padding.

Key fields used in the parser:

| Bit | Field | Size | Notes |
|---|---|---|---|
| 2 | Rate | 1B | × 0.5 Mbps |
| 3 | Channel | 4B | Frequency (2B) + flags (2B) |
| 5 | dBm Signal | 1B | **Signed byte** — this is the RSSI |
| 11 | Antenna | 1B | Antenna index |

**Why RSSI is a signed byte**: Signal levels are always negative (below the noise floor reference). Range is typically -100 to -20 dBm. The parser uses `struct.unpack("b", ...)` (lowercase b = signed) to get the correct negative value.

**Frequency → Channel mapping**: The Channel field gives frequency in MHz, not the channel number. The parser maps these with a lookup table (e.g. 2437 MHz → Channel 6, 5745 MHz → Channel 149).

## RSSI Signal Strength Reference

From practical captures with the ESP32:

| RSSI Range | Signal Quality | Typical Distance (indoor) |
|---|---|---|
| > -50 dBm | Excellent | Same room, < 5m |
| -50 to -67 dBm | Good | Within same floor |
| -67 to -80 dBm | Fair | Adjacent room / floor |
| -80 to -90 dBm | Poor | Edge of range |
| < -90 dBm | Unusable | Noise floor |

The ESP32's WiFi receiver has a sensitivity of approximately -97 dBm (datasheet), so captures below -90 dBm are at the noise floor edge and may be unreliable.

## Monitor Mode vs Managed Mode

| | Monitor Mode | Managed Mode |
|---|---|---|
| Association required | No | Yes |
| Sees all frames | Yes | Only frames addressed to device |
| Can inject frames | Yes (hardware dependent) | Limited |
| ESP32 API | `esp_wifi_set_promiscuous(true)` | Default station/AP mode |
| Frame format received | Raw 802.11 + radiotap | Processed, stripped |

The ESP32 promiscuous callback receives the full 802.11 frame including the radiotap header prepended by the driver. The callback function signature in ESP-IDF is:

```c
void wifi_sniffer_packet_handler(void *buff, wifi_promiscuous_pkt_type_t type) {
    wifi_promiscuous_pkt_t *pkt = (wifi_promiscuous_pkt_t *)buff;
    // pkt->rx_ctrl contains RSSI, channel, timestamp
    // pkt->payload contains the raw 802.11 frame
}
```

The `rx_ctrl` struct (`wifi_pkt_rx_ctrl_t`) already provides parsed RSSI and channel, so in practice the radiotap header is more relevant when analyzing captures made with Linux tools (Wireshark, airodump-ng) than with ESP32 directly.

## PCAP vs PCAPNG Format

| | PCAP | PCAPNG |
|---|---|---|
| Magic bytes | `0xA1B2C3D4` | `0x0A0D0D0A` |
| Byte order | From magic | SHB byte-order magic field |
| Multi-interface | No | Yes (Interface Description Blocks) |
| Timestamps | Microseconds | Configurable per IDB |
| Metadata | Minimal | Rich (comments, interface info, statistics) |
| Wireshark default | Old | New (since Wireshark 1.8) |

PCAPNG is the modern standard. The ESP32 firmware typically produces raw PCAP, but Wireshark saves in PCAPNG by default. The parser handles both.
